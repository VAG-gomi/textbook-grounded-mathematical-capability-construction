2. The root README should explain the experiment

Something approximately like:

Orders: Mathematical Capability Construction

Purpose
-------
This repository investigates whether progressively different
computational capabilities can be constructed from explicit
mathematical specifications and minimal executable mechanisms.

Method
------
Mathematical specification
        ↓
Logical necessity
        ↓
Minimal implementation
        ↓
Adversarial testing
        ↓
Capability classification

Rules
-----
1. A new Order must introduce a demonstrable capability.
2. Possibility is not treated as necessity.
3. Implementation evidence is not experimental evidence.
4. Tests must attempt to falsify the claimed distinction.
5. Later capabilities must not be silently imported into earlier Orders.
6. Failed investigations remain part of the research record.

That last point is particularly important.

Do not delete the failed O3 investigation.

It is evidence.

3. Every Order should have the same forensic template

For example, order05/specification.md should answer:

Mathematical object

\[
\theta_t\in\{0,1\}
\]

Input

\[
y_t\in\{0,1\}
\]

Prediction

\[
\hat y_t=\theta_t
\]

Error

\[
e_t=y_t-\hat y_t
\]

Update

\[
\theta_{t+1}=
\begin{cases}
y_t & e_t\neq0\\
\theta_t & e_t=0
\end{cases}
\]

Claimed capability

> Persistent error-driven correction of a single binary value.



What it does NOT establish

general learning

function learning

generalisation

neural computation

intelligence

optimisation


This prevents the repository from gradually turning into a collection of exaggerated claims.


---

4. Most importantly: every Order needs a boundary test

This is probably the most important thing I'd add.

Don't only test:

> “Does O5 work?”



Test:

> “Can O4 do this?”



For every Order:

\[
\boxed{\text{New capability} + \text{previous-order counterexample}}
\]

For example:

O6's claim

O6 learns an input-output relationship.

So your test shouldn't merely show:

input 0 → target 1
input 1 → target 0

It should demonstrate something O5 cannot represent:

same learner
input 0 → 1
input 1 → 0

because O5 only has one persistent parameter/value.

That's the actual capability boundary.

5. O3 deserves special treatment

Don't pretend the numbering problem never happened.

I'd explicitly document:

ORDER 3 STATUS

Formal:
PASS

Behavioural:
DEGENERATE

Reason:
T3(s,x) = T2(s,x) for all admissible inputs.

Therefore:
O3 does not establish a new behavioural capability.

The +1 variant was investigated but rejected as
a forced milestone because +1 is not mathematically
necessitated by O1/O2.

Then put Manus's investigation in:

investigations/order03_forced_capability.md

That is actually one of the strongest pieces of methodological evidence in the repository.

6. Keep implementation and experiment separate

This distinction from your methodology becomes extremely important.

For example:

implementation/

answers:

> Does the program execute the specification?



Whereas:

experiments/

answers:

> Does the claimed capability actually distinguish itself from the previous Order?



And:

investigations/

answers:

> Did we discover contradictions, degeneracies, or failed candidates?



So don't let:

pytest: 47 passed

become:

> “Order 7 is scientifically validated.”



Those are different claims.

Keep it separate:

\[

\[

That separation will make the eventual result much more interesting either way.
