Repository Construction Instructions for Manus

0. Mission

Maintain and upgrade the repository:

"VAG-gomi/textbook-grounded-mathematical-capability-construction"

The repository is a research record for textbook-grounded mathematical capability construction.

The purpose is not to maximise code complexity, produce an AI system, or force a sequential O1–O8 numbering.

The governing methodology is:

[
\boxed{
\text{Mathematical specification}
\rightarrow
\text{Logical necessity}
\rightarrow
\text{Minimal executable mechanism}
\rightarrow
\text{Adversarial testing}
\rightarrow
\text{Capability classification}
}
]

The repository must preserve the distinction between:

- what the textbook establishes,
- what is logically forced,
- what is merely a valid construction,
- what is implemented,
- what is experimentally demonstrated,
- and what remains hypothetical.

Do not silently strengthen claims.

Do not invent missing mathematical justification merely to make the sequence look cleaner.

3. Required repository philosophy

For every capability claim, distinguish these questions:

A. What exists mathematically?

Example:

[
d=|x-a|
]

B. What is logically forced?

Example:

Does the limitation of the previous Order require this new mathematical object?

C. What implementation was selected?

Example:

Python class using a boolean determination.

D. What was experimentally demonstrated?

Example:

A counterexample that the previous Order cannot reproduce.

E. What remains unestablished?

Example:

Generalisation, intelligence, neural equivalence, unrestricted learning, etc.

Never collapse A–E into a single "validated" label.

---

4. Epistemic labels

Use these labels consistently:

- FACT — directly supported by source, code, or reproducible test.
- INFERENCE — follows from established facts but is not directly stated by the source.
- HYPOTHESIS — proposed mechanism or interpretation.
- CONSTRUCTION — a deliberately selected implementation choice.
- IMPLEMENTATION EVIDENCE — code executes the specified mechanism.
- EXPERIMENTAL EVIDENCE — an executed test distinguishes competing claims.
- VERIFIED — only use when the stated verification condition has actually been satisfied and is reproducible.

Do not use "proved" where the repository only has an executed example.

No Order claims more than its evidence establishes.

The repository should embody one central rule:

[
\boxed{
\text{Do not add a capability because it can be constructed.}
}
]

Instead:

[
\boxed{
\text{Add a capability when the previous mechanism has a demonstrated limitation that requires it.}
}
]

And equally:

[
\boxed{
\text{Do not confuse implementation success with capability validation.}
}
]

The strongest outcome of this repository is not that it produces eight increasingly complicated programs.

The strongest outcome is that it can show exactly why each capability was admitted, why each rejected capability was rejected, and where the evidence stops.
